# 주문 화면 영향 범위 정리

> 작성: 2026-09-01 · 기준 브랜치: `refactor/iss249`
> 완료 시 이 문서는 주문 도메인 리팩토링의 기준 자료로 유지한다.

## 목적

V2 주문 기능 개선 전에 프론트엔드에서 영향을 받는 화면, API, 타입, 유틸, 검증 로직을 정리한다.
이 문서는 기능 구현 문서가 아니라 이후 작업 범위를 나누기 위한 기준 문서다.

## 프론트에서 먼저 진행 가능한 작업

1. 주문 페이지 컴포넌트 분리
   - 주문자 정보 입력 영역
   - 수령 방식/주소 입력 영역
   - 주문 상품 목록 영역
   - 금액 요약 영역
   - 제출 버튼/검증 메시지 영역

2. 주문 금액 표시 UI 정리
   - 상품 금액, 배송비, 최종 결제 금액을 분리해서 표시할 수 있는 UI 구조 준비
   - 실제 배송비 정책 확정 전에는 기존 계산 로직을 변경하지 않는다.

3. 수령 방식 UI 구조 정리
   - 현장수령/택배 선택 영역을 독립 컴포넌트로 분리
   - 배송비, 주소 검증, 현장수령 안내는 정책 확정 후 연결한다.

4. 주문 상세 표시 컴포넌트 정리
   - 주문번호, 주문 상태, 수령 방식, 결제 정보, 개인정보 마스킹 표시 위치를 명확히 한다.
   - 실제 마스킹 정책은 BE/API 응답 정책과 맞춘 뒤 반영한다.

5. 관리자 주문 목록 필터 UI 구조 정리
   - 프로젝트, 기간, 주문번호, 주문자, 연락처, 상태, 수령 방식 필터 영역을 분리할 수 있게 준비
   - 실제 필터 API 파라미터는 BE 계약 확정 후 연결한다.

## BE/API 정책 확정 후 진행할 작업

- 회원 주문과 비회원 주문 식별 방식
- 주문 조회용 식별값과 회원 ID 분리
- 내부 주문 ID와 표시용 주문번호 분리
- 프로젝트별 주문번호 생성 주체
- 주문과 프로젝트 관계 저장 방식
- 주문 상태와 배송 상태 분리 여부
- 주문 상태 변경 이력 저장 여부
- 배송비 계산 주체와 제주/도서산간, 무료배송 예외 정책
- 재고 차감, 주문 취소, 환불 시 재고 복구 정책
- 개인정보 마스킹 기준과 스프레드시트 다운로드 권한

## 추천 구현 순서

1. `refactor`: 주문 페이지 컴포넌트 분리
2. `fix`: 상품 이미지 잘림 현상 수정
3. `refactor`: 주문 금액 표시 UI 구조 정리
4. `refactor`: 수령 방식 입력 UI 구조 정리
5. `refactor`: 관리자 주문 목록 필터 UI 구조 정리
6. `feat`: BE API 계약 확정 후 주문 조회 오류 개선
7. `feat`: BE API 계약 확정 후 프로젝트별 주문 관리
8. `feat`: BE API 계약 확정 후 배송비/재고 재검증 연결

## 이번 문서 기준으로 하지 않을 작업

- 회원/비회원 주문 데이터 구조 변경
- 주문번호 체계 실제 변경
- 배송비 계산 로직 변경
- 주문 상태 enum 변경
- 재고 차감/복구 구현
- 스프레드시트 다운로드 API 연동
