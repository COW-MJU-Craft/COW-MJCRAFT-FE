# GA4 구축 플레이북 (범용)

명지공방·자빈스튜디오 두 프로젝트에 실제로 GA4를 붙이면서 겪은 것을 합친 문서. 다음에 새 프로젝트(예: 자빈랩)에 GA4를 붙일 때는 이 문서부터 본다.

- 최종 갱신: 2026-11-26 (FE main `5223a57`, BE main `642406a` 기준)
- 명지공방이 지금 어디까지 만들어졌는지, 어떻게 동작하는지, 운영할 때 무엇을 조심해야 하는지는 **8절**에 모아 두었다.
- 이 문서는 일회성 인계 문서가 아니라 계속 고쳐 쓰는 문서다. 내용이 바뀌면 위 갱신 기준점도 같이 고친다.

## 0. 먼저 정할 것 — 코드에 직접 붙이나, GTM으로 붙이나

| | 코드에 직접 (`gtag.js`) | GTM 경유 |
| --- | --- | --- |
| 사례 | 명지공방 (Vite + React SPA) | 자빈스튜디오 (Next.js App Router) |
| 측정 ID를 코드에 넣나 | 넣는다 (빌드 환경변수) | 안 넣는다 — GTM 컨테이너 안에서만 다룸 |
| 새 이벤트 추가할 때 | 코드 수정 + 배포 필요 | GTM 콘솔에서 변수/트리거/태그만 추가하면 됨 (배포 불필요) |
| 초기 세팅 난이도 | 낮음 | 조금 더 복잡함 (변수·트리거·태그를 따로 만들어야 함) |
| 추천 상황 | 이벤트 스키마가 거의 안 바뀌는 작은 사이트 | 마케팅/운영팀이 이벤트를 자주 추가·조정하는 사이트 |

둘 다 아래 1절(공통)은 똑같이 적용된다.

## 1. 공통 — 방식과 무관하게 매번 해야 하는 것

1. **GA4 속성 만들기**: 시간대 Asia/Seoul, 통화 KRW, 데이터 보관 14개월.
2. **"브라우저 기록 이벤트 기반 페이지 변경" 끄기** (관리 → 데이터 스트림 → 향상된 측정 → 페이지 조회 → 고급 설정). 코드가 라우트 변경마다 직접 `page_view`를 보내는 구조(SPA, Next.js App Router 등)라면 **반드시 꺼야 한다** — 안 끄면 GA4가 자동으로도 하나 더 보내서 페이지뷰가 두 배로 잡힌다. 자빈스튜디오에서 실제로 이걸 놓쳐서 숫자가 부풀어 올랐던 적이 있다. 이 옵션은 코드의 경로 제외 로직(`/admin` 등)도 거치지 않고 독자적으로 발동하므로, 꺼두지 않으면 관리자 방문도 그대로 섞인다.
3. **내부 트래픽 정의를 먼저 만들고 그다음 필터를 활성화**한다. 데이터 필터의 "Internal Traffic"은 기본 "테스트" 상태라 아무것도 거르지 않고, IP 규칙(내부 트래픽 정의)이 하나도 없으면 필터를 활성화해도 의미가 없다. 순서: 데이터 스트림 → 태그 설정 구성 → 내부 트래픽 정의 → 팀원 IP 추가 → 그다음 데이터 필터를 테스트→활성으로 전환.
4. **맞춤 이벤트를 쓴다면 GA4 맞춤 정의(측정기준/측정항목)를 등록**한다. 등록 전 데이터는 소급 적용되지 않으니 가능한 한 빨리 등록한다.
5. **UTM 규칙**: `utm_source`/`utm_medium`/`utm_campaign`(선택 `utm_content`), 값은 항상 영문 소문자, 캠페인마다 값 하나로 통일, 링크 스프레드시트 공유.
6. **키 이벤트**: 리드/구매 등 진짜 전환에 해당하는 이벤트를 관리 → 키 이벤트에 등록해야 전환으로 집계된다. 사이트마다 이름이 다르면(`order_submit`, `generate_lead` 등) 직접 등록해야 한다.
7. **배포/게시 전에는 아무 데이터도 안 쌓인다**는 전제로 움직인다. GA4는 수집 시작 이전을 소급하지 않는다.

## 2. 방식 A: 코드에 `gtag.js` 직접 붙이기 (명지공방 사례)

- 측정 ID를 빌드 환경변수(Vite는 `VITE_`, Next.js는 `NEXT_PUBLIC_`)로 넣고, `gtag('config', ID, { send_page_view: false })`로 자동 page_view를 끈 뒤 라우트 변경마다 직접 전송한다.
- `gtag` 함수는 반드시 `(...args) => dataLayer.push(arguments)`처럼 **arguments 객체**를 넣어야 한다. 일반 배열을 넣으면 GA가 명령으로 인식하지 못해 **몇 달째 0건**이 되는데도 코드/네트워크 요청상으로는 멀쩡해 보여서 원인 찾기가 특히 어렵다. 확인은 브라우저 Network에서 `google-analytics.com/g/collect` 요청이 실제로 나가는지로 한다.
- Docker/Coolify 등으로 배포할 때는 빌드 단계(`ARG`+`ENV`)에 측정 ID를 반드시 넘겨야 한다. 런타임에 환경변수를 바꿔도 이미 빌드된 번들에는 반영되지 않는다.
- 관리자 화면 방문을 빼고 싶으면 `window['ga-disable-측정ID'] = true`(GA 공식 차단 스위치)를 관리자 세션 동안 켠다. 명지공방은 로그인 상태와 이 스위치를 동기화한다(8-2절).

## 3. 방식 B: GTM 경유 (자빈스튜디오 사례)

1. GTM 컨테이너를 만들고, 사이트 코드에는 GTM 컨테이너 ID만 넣어서 `gtm.js` 스크립트를 주입한다(측정 ID는 코드에 넣지 않는다).
2. GTM에서 **"Google 태그"** 타입으로 GA4 구성 태그를 하나 만들고(트리거: All Pages/Initialization), 측정 ID는 거기에만 넣는다.
3. 코드가 보내는 커스텀 이벤트 파라미터 하나당 **데이터 영역 변수**를 만든다.
4. 커스텀 이벤트 이름들을 정규식으로 묶은 **맞춤 이벤트 트리거 1개**를 만든다 (이벤트마다 트리거를 따로 만들 필요 없음 — `^(event1|event2|...)$` 정규식 하나로 충분).
5. **"GA4 이벤트"** 태그 1개를 만들어 "설정 태그"로 위 Google 태그를 선택하고, 이벤트 이름은 `{{Event}}`(기본 제공 변수), 이벤트 매개변수에 3번 변수들을 전부 연결한다. 이것도 이벤트마다 태그를 따로 만들 필요 없이 **태그 1개로 전체 커스텀 이벤트를 처리**할 수 있다.
6. 미리보기로 확인 후 반드시 **제출(게시)**한다 — 미리보기만으로는 실제 방문자에게 반영되지 않는다.
7. GTM API(Tag Manager API v2)로 2~5번을 자동화하는 스크립트가 자빈스튜디오 레포의 `scripts/gtm-automate.mjs`에 있다. 변수/트리거 생성은 구글 공식 스키마 기준으로 작성해서 신뢰도가 높고, GA4 이벤트 태그의 "설정 태그" 연결 부분은 구글이 비공식적으로만 지원해서 생성 후 GTM 화면에서 직접 확인이 필요하다. 인증은 `gcloud`의 기본 OAuth 클라이언트로는 Tag Manager 스코프가 차단되므로, GCP 콘솔에서 직접 만든 OAuth 클라이언트(Desktop app)를 `--client-id-file`로 지정해서 `gcloud auth application-default login` 해야 한다.

## 4. GTM/GA4 콘솔 실전 팁 (자빈스튜디오 실제 등록 과정에서 겪은 것)

가이드에는 안 나오는, 화면에서 직접 클릭해보다가 헷갈렸던 것들.

**GA4 관리자 화면과 GTM은 완전히 다른 사이트다.** "변수", "트리거" 메뉴는 GA4(`analytics.google.com`)에 없다 — 전부 GTM(`tagmanager.google.com`) 안에만 있다. GA4 관리 화면에 들어가서 "변수가 어디 있냐"고 헤매는 게 가장 흔한 삽질이다.

**GTM 왼쪽 메뉴가 기본으로는 "개요/설정/태그"만 보인다.** "트리거", "변수", "폴더", "템플릿"은 그 아래 **"자세히 보기"**를 클릭해야 펼쳐진다.

**이벤트 수만큼 변수·트리거·태그를 10개씩 만들 필요 없다** (3절 4~5번 참고). 트리거는 이벤트 이름들을 정규식(`^(a|b|c)$`, "정규식 일치 사용" 체크)으로 묶은 것 1개, 태그도 이벤트 이름 자리에 기본 제공 변수 `{{Event}}`를 넣은 것 1개로 전체 이벤트를 다 처리할 수 있다. 다만 `{{Event}}`가 변수 목록에 안 보이면, 변수 → 기본 제공 변수 → 구성 → **"Event"** 체크박스를 켜야 한다.

**데이터 영역 변수를 만들 때 "데이터 영역 버전", "기본값 설정", "값 형식" 같은 나머지 옵션은 전부 기본값 그대로 두면 된다.** 딱 "데이터 영역 변수 이름" 칸에 코드가 보내는 파라미터 키(`cta_name` 등)만 정확히 입력하면 끝.

**헷갈리기 쉬운 함정: "Google 태그: 이벤트 설정"이라는 별도 변수 타입이 있는데, 이게 GA4 이벤트 태그 안의 "이벤트 매개변수" 섹션이랑 화면이 완전히 똑같이 생겼다.** 이벤트 이름 필드 옆 변수 선택 아이콘을 잘못 눌러서 이 변수를 새로 만드는 쪽으로 빠지기 쉬운데, 우리가 채워야 할 건 그게 아니라 **GA4 이벤트 태그 자체 안에 있는 "이벤트 매개변수" 섹션**이다. 헷갈리면 태그를 닫고 다시 열어서 "이벤트 이름" 바로 아래 섹션을 펼쳐서 채운다.

**GA4 이벤트 태그의 측정 ID 연결 방식이 계정마다 두 가지로 다르게 보일 수 있다**: ① "설정 태그" 드롭다운에서 기존 Google 태그(구성 태그)를 선택하는 방식, ② "측정 ID" 칸에 `G-...` 값을 직접 타이핑하는 방식. 둘 다 정상이고, 화면에 보이는 대로 하면 된다.

**과거에 이미 만들어놓고 제출(게시)을 안 해서 몇 달째 방치된 태그가 있을 수 있다.** 태그 목록과 "버전" 탭을 먼저 확인한다 — "이미 돼 있는 줄 알았는데 사실 한 번도 게시된 적이 없었다"는 패턴이 실제로 있었다.

**작업하다 보면 GTM이 "Google Analytics" 타입의 중복 태그를 자동으로 하나 더 만들어주는 경우가 있다** — 이미 있는 "Google 태그"(구성 태그)와 측정 ID·트리거가 똑같은 중복이라, 발견하면 지운다(중복 그대로 둬도 GA4 쪽 "중복 인스턴스 무시" 기능이 있어 치명적이진 않지만, 깔끔하지 않다).

**GA4 관리자 화면에서 "속성 세부정보"(시간대/통화) 찾기 힘들면, 왼쪽 메뉴를 헤매지 말고 `analytics.google.com/analytics/web/#/admin` 링크로 바로 들어간다.**

**테스트 확인은 시크릿창 + GA4 "실시간"(또는 홈 화면의 "지난 30분 동안의 활성 사용자" 카드)으로 한다.** 숫자가 1이라도 뜨면 그 즉시 연결이 살아있다는 뜻이다.

**Tag Manager API로 자동화하려다 만난 인증 삽질:**

- `gcloud auth application-default login --scopes=...`에 Google Cloud 외의 스코프(Tag Manager 등)를 하나라도 넣으면, `cloud-platform` 스코프를 같이 넣으라는 에러가 난다.
- 그래도 안 되면("이 앱이 차단되었습니다"), `gcloud`의 기본 OAuth 클라이언트 자체가 그 스코프에 대해 검증이 안 돼 있어서 막힌 것이다. GCP 콘솔에서 직접 OAuth 클라이언트(Desktop app 타입)를 만들어 다운로드한 다음 `gcloud auth application-default login --client-id-file=<다운로드한 JSON 경로> --scopes=...`로 로그인해야 한다. 이 경우엔 `cloud-platform`을 억지로 넣을 필요는 없다.
- 설정 단계 자체가 변수 10여 개 수동으로 클릭하는 것보다 오래 걸릴 수 있다 — 반복적으로 여러 프로젝트에 자동화할 게 아니면 그냥 수동으로 끝내는 게 더 빠르다.
- pnpm 워크스페이스 루트에서 새 패키지 설치할 때 `pnpm add <pkg>`가 `ERR_PNPM_ADDING_TO_ROOT`로 막히면 `-w` 플래그(`pnpm add <pkg> -w`)를 붙인다.

## 5. 실제 겪은 함정 모음 (두 프로젝트 합산)

| 증상 | 원인 | 대응 |
| --- | --- | --- |
| 실시간 보고서에 몇 달째 0건, 에러도 없음 | `gtag`를 일반 배열로 정의(방식 A) | `function(){ dataLayer.push(arguments) }`로 수정, Network에서 `g/collect` 확인 |
| 페이지뷰가 실제보다 약 두 배 | 향상된 측정의 "브라우저 기록 이벤트 기반 페이지 변경"이 켜진 채로, 코드도 직접 page_view 전송 | 그 옵션을 끈다 (공통 1-2) |
| 관리자 방문이 일반 트래픽에 섞임 | 코드의 경로 제외 로직이 GA4 자동 페이지뷰는 거치지 않음 | 위와 동일 옵션을 끄거나, `ga-disable-ID` 스위치 사용 |
| Internal Traffic 필터 켰는데 팀 방문이 그대로 잡힘 | 내부 트래픽 정의(IP 규칙)를 안 만듦 | 정의를 먼저 만들고 필터를 테스트→활성으로 전환 |
| 로컬/프리뷰에서 아무리 테스트해도 안 잡힘 | 코드가 운영 도메인에서만 전송하도록 게이트돼 있음(의도적) | 운영 배포 후 확인, 급하면 게이트를 일시 완화 후 원복 |
| 커스텀 이벤트가 GA4 탐색에서 안 보임 | 맞춤 측정기준/항목 미등록 | 관리 → 맞춤 정의에 등록 |
| GTM 미리보기엔 뜨는데 실데이터 없음 | 제출(게시)을 안 함 | 게시까지 완료 |
| Looker Studio 차트마다 "시스템 오류" | UA용 템플릿을 고름 | "GA4 Report" 템플릿 사용 |
| Looker Studio가 온통 "데이터 없음" | 기본 날짜 범위가 "어제까지"라 수집 첫날이 빠짐 | 날짜 범위에 오늘 포함 |
| 관리자로 로그인한 채 쓴 활동이 방문자 집계에 섞임 | 로그인 상태와 무관하게 전송, 향상된 측정의 자동 page_view까지 겹침 | `ga-disable-ID` 스위치를 로그인 상태와 동기화 (8-2절) |
| 어드민 분석 화면이 "분석 연동이 아직 설정되지 않았어요" | BE에 `GA_PROPERTY_ID` 또는 `GA_CREDENTIALS_BASE64`가 없거나, 넣고 재배포를 안 함 | BE 앱 환경변수 확인 후 BE 재배포 (8-5절) |
| CI의 secret-scan이 모든 PR에서 실패 | 테스트 코드의 `const key = '...'`가 gitleaks `generic-api-key`로 오탐. 스캔이 열려 있는 모든 브랜치의 커밋을 훑어서 한 브랜치의 오탐이 전체 PR을 막음 | 리터럴을 조합식으로 바꾸고 `.gitleaksignore`에 지문 등록 (8-7절) |
| 서비스 계정 키(JSON 또는 그 Base64)를 메신저나 채팅에 붙여넣음 | 비밀 키가 그대로 들어 있음 | 해당 키를 즉시 삭제하고 새로 발급 (8-5절) |

## 6. 데이터 보는 법 + 팀원 권한 + API

- 실시간(최근 30분)과 일반 보고서(반영까지 몇 시간~최대 이틀)는 용도가 다르다. 배포 직후 확인은 항상 실시간으로.
- 팀원은 관리 → 속성 액세스 관리에서 이메일로 개별 추가(기본 역할: 뷰어). 공용 계정 하나를 돌려 쓰지 않는다.
- Looker Studio로 팀 공유용 대시보드를 무료로 만들 수 있다("GA4 Report" 템플릿에서 시작).
- 코드/AI로 데이터를 꺼내려면 GCP 서비스 계정을 만들어 GA4 속성에 뷰어로 추가하고, Google Analytics Data API를 활성화한다. 이 경로는 읽기 전용이고, 서비스 계정 키(JSON)는 반드시 비밀값으로 다룬다(저장소에 커밋 금지).

## 7. 자체 어드민에 GA4 통계 내장하기 — 자빈스튜디오 사례

매번 analytics.google.com에 들어가지 않고, 이미 있는 어드민 화면 안에서 숫자를 바로 보고 싶을 때의 패턴이다.

- 공식 Node 클라이언트 `@google-analytics/data`의 `BetaAnalyticsDataClient`를 써서, 어드민 페이지가 **요청마다** GA4 Data API를 호출한다. DB에 따로 저장/캐싱하지 않는다 — 단순하고, 숫자가 항상 최신이다.
- 인증은 5절의 서비스 계정 JSON을 기존 비밀값 관리 방식(`.env.local` + 운영 환경변수)에 그대로 올려서 쓴다. GCS 같은 다른 구글 연동이 이미 있다면 그거랑 똑같은 패턴(`JSON.parse(process.env.XXX_SERVICE_ACCOUNT_KEY)`)을 재사용하면 된다.
- 맞춤 측정기준으로 세분화한 통계(예: 어떤 CTA가 많이 눌렸는지)는 4절처럼 GA4 쪽 맞춤 정의 등록이 먼저 돼 있어야 API에서도 조회된다. 등록 안 돼 있어도 에러로 페이지 전체가 깨지지 않도록, 카드 하나 단위로 실패를 흡수하는 방어 코드를 둔다.
- 참고 구현: 자빈스튜디오 레포의 `lib/ga4-report.ts` (API 호출부), `app/admin/(dashboard)/analytics/page.tsx` (화면), 둘 다 그대로 복붙해서 프로젝트 이름/이벤트 스키마만 바꾸는 식으로 재사용 가능하다.
- 백엔드가 따로 있는 구조(React SPA + Spring Boot 등)는 명지공방 방식을 쓴다. 브라우저에 서비스 계정 키를 둘 수 없으므로 BE가 GA를 호출하고 FE는 집계 결과만 받는다(8-4절).

## 8. 명지공방 구현 상세 (React SPA + Spring Boot)

명지공방에서 실제로 만든 것, 동작 방식, 운영 시 주의점이다. 속성 ID `536574599`(비밀값 아님), 서비스 계정 `ga4-reader`(GCP 프로젝트 `mju-craft-ga4-mcp-20261121`, GA 속성에는 뷰어 권한만).

### 8-1. 전체 구조

```text
방문자 브라우저 --gtag--> Google Analytics 4
                              ^
관리자 화면(/admin/analytics) --> BE GET /api/admin/analytics/channels --(서비스 계정, REST)--> GA4 Data API
```

- 수집은 FE가, 조회는 BE가 맡는다. 브라우저에는 GA 인증 정보가 없다.
- 수집 코드는 `src/utils/common/analytics.ts`, 라우트별 전송은 `src/components/analytics/GoogleAnalytics.tsx`, UTM·유입 분류는 `src/utils/common/analyticsAttribution.ts`.

### 8-2. 수집 (FE)

- 측정 ID는 빌드 환경변수 `VITE_GA4_MEASUREMENT_ID`로 넣고, Docker 빌드 인자로 넘긴다. 자동 page_view는 끄고(`send_page_view: false`) 공개 경로의 라우트 변경마다 직접 전송한다. `/admin` 경로는 직접 전송에서 제외한다.
- 전송하는 이벤트: `page_view`, `view_item`, `add_to_cart`, `view_cart`, `begin_checkout`, `order_submit`(주문 제출), `external_link_click`.
- 이벤트에는 유입 정보 파라미터(`acquisition_channel`, `ai_source`, `landing_path`, `link_domain`)를 함께 보낸다. UTM이 있으면 우선 쓰고, 없으면 리퍼러로 채널을 분류한다. ChatGPT 등 AI 어시스턴트 유입도 `ai_source`로 구분한다.
- **관리자 활동 제외**: 관리자는 로그인이 곧 관리자다. `GoogleAnalytics` 컴포넌트가 로그인 상태(`isLoggedIn`)와 인증 변경 이벤트(`auth-changed`)를 구독해서 `window['ga-disable-<측정ID>']`를 켜고 끈다. 로그인한 동안은 향상된 측정의 자동 전송까지 포함해 모든 전송이 막히고, 로그아웃하면 바로 풀린다. 이 스위치 적용 전 기간에는 운영진의 테스트 방문이 섞여 있다.
- 관리자 메뉴: 상단 **유입 분석**(`/admin/analytics`, 자체 화면), **GA ↗**(`analytics.google.com` 새 탭). 주소는 `src/constants/adminLinks.ts` 한 곳에서 관리한다.

### 8-3. 어드민 "유입 분석" 화면 (FE)

- 요약 숫자(세션, 상품 조회 사용자, 주문 사용자, 전환율), 일별 방문 막대 그래프, 채널별 방문→주문 표. 기간은 최근 7·14·30·90일과 직접 지정(최대 366일).
- UTM 캠페인 이름이 있는 행은 캠페인 이름을 같이 보여 준다. GA가 UTM 없는 방문에 채우는 `(referral)`, `(direct)` 같은 값은 캠페인으로 표시하지 않는다.
- GA는 방문이 없는 날을 응답에서 빼므로 FE가 빈 날짜를 0으로 채워 그래프 날짜가 건너뛰지 않게 한다.
- 로딩 중에는 실제 화면과 같은 배치의 스켈레톤을 보여 준다. 오류는 상황별 문구(400/401/502/503)로 안내한다.
- 순수 로직(채널 이름, 전환율, 한국 시간 날짜 계산, 기간 검증, 빈 날짜 채우기)은 `src/utils/admin/analytics.ts`에 분리하고 테스트가 있다.

### 8-4. 조회 API (BE)

- `GET /api/admin/analytics/channels?from=yyyy-MM-dd&to=yyyy-MM-dd` (관리자 전용, 기간 최대 366일).
- 응답: `channels[]`(source, medium, campaign, sessions, users, viewItem, addToCart, beginCheckout, orders)와 `daily[]`(date, sessions, users). 퍼널 단계는 `view_item`, `add_to_cart`, `begin_checkout`, `order_submit`을 한 **사용자 수**다.
- GA Data API를 **REST**로 부른다(gRPC 클라이언트를 쓰지 않아 의존성이 작다). 서비스 계정 토큰만 `google-auth-library`로 발급한다(읽기 전용 스코프). 보고서 3개(채널별 세션, 채널별 퍼널 이벤트, 일별 방문)를 부른다.
- 같은 기간의 결과는 15분 캐시한다(인메모리, 최대 50개. 단일 인스턴스 전제라 스케일아웃하면 교체해야 한다).
- 오류: 기간 오류 400, GA 호출 실패 502, 연동 설정 없음 503. 설정이 없어도 서버는 정상 기동하고 이 API만 503을 준다. 에러 로그에는 예외 종류만 남기고 응답 본문과 토큰은 남기지 않는다.
- 코드 위치: `domain/analytics/` (controller, service, dto, config, exception). 테스트는 서비스 집계·캐시·검증, GA 응답 파싱·요청 생성을 다룬다.

### 8-5. 환경변수와 서비스 계정 키

BE 앱(Coolify)에 아래를 넣고 **BE를 재배포**한다. 환경변수는 재시작해야 적용된다.

| 키 | 값 | 비고 |
| --- | --- | --- |
| `GA_PROPERTY_ID` | `536574599` | 비밀값 아님 |
| `GA_CREDENTIALS_BASE64` | `ga4-reader` 키(JSON)를 Base64로 바꾼 값 | **비밀값**. 한 줄 |
| `GA_CACHE_TTL` | 선택. 기본 `PT15M` | ISO-8601 기간 |

Coolify 입력 옵션: Value type은 Single line, **Build time은 끄고** Runtime만 켠다. 비밀값은 빌드에 넣을 이유가 없다.

키 만들기:

1. GCP 콘솔의 해당 프로젝트 → IAM 및 관리자 → 서비스 계정 → `ga4-reader` → **키** 탭 → 키 추가 → 새 키 만들기 → JSON.
2. 터미널에서 Base64로 바꿔 클립보드에 복사한다. 화면에는 아무것도 안 나오는 게 정상이다.
   ```bash
   base64 -i ~/Downloads/<내려받은파일>.json | tr -d '\n' | pbcopy
   ```
3. **채팅·메신저·저장소에 붙여넣지 말고** Coolify의 Value 칸에 바로 붙여넣는다. 값이 `ey`로 시작하면 JSON을 변환한 정상 형식이다.
4. 저장하고 BE를 재배포한 뒤 원본 JSON 파일을 삭제하고 휴지통도 비운다.
5. 키 목록에 보이는 40자리 16진수는 키 ID(번호표)일 뿐 비밀이 아니다. 실제 비밀은 JSON 안의 `private_key`다.
6. **키나 그 Base64가 어디든 노출됐다면** 같은 키 탭에서 해당 키를 삭제하고 새로 발급한다. 삭제하면 그 키로는 즉시 접근할 수 없다. 조직이 없는 프로젝트(명지공방의 GA 프로젝트가 그렇다)는 대개 키 생성이 막히지 않는다. 조직 정책으로 막혀 있으면 정책 예외를 요청해야 한다.

### 8-6. 배포 순서와 확인

1. BE를 먼저 배포한다(develop→main 병합은 BE 규칙상 **사람이** 한다). FE만 먼저 올라가면 화면에 "분석 연동이 아직 설정되지 않았어요"가 보이는데, 서버에 문제는 없다.
2. Coolify BE 환경변수 추가 → BE 재배포.
3. FE는 main 병합 후 이미지 빌드가 끝나면 Coolify에서 Redeploy한다. `Build & Push` 워크플로우의 웹훅 단계는 실패로 표시될 수 있지만 수동 Redeploy로 정상 배포된다. 운영 `/version.json`의 sha가 main 최신 커밋과 같은지로 확인한다.
4. 관리자로 로그인해 `/admin/analytics`에 숫자가 나오면 연동 성공이다.
   - "분석 연동이 아직 설정되지 않았어요": 환경변수가 BE 앱에 없거나 재배포 전이다.
   - "Google Analytics에서 데이터를 가져오지 못했어요": 키 값을 잘못 복사했거나 권한 문제다.
5. 로그인 없이는 이 API를 확인할 수 없다(401). health가 200이어도 GA 연동 여부는 알 수 없다.

### 8-7. 작업 규칙과 CI에서 겪은 것

- FE PR 브랜치는 `iss/{이슈번호}`만 허용된다(`validate-pr-base`). `feat/...` 이름으로 올리면 이 검사가 실패한다. FE는 작업 PR을 squash로 develop에, develop→main은 merge commit으로 병합한다.
- BE는 `main`·`develop` 병합을 **사람만** 한다(BE `AGENTS.md` 절대 규칙).
- `secret-scan`(gitleaks v8.21.2)은 **열려 있는 모든 브랜치의 모든 커밋**을 훑는다. 아직 병합되지 않은 브랜치 하나에 오탐이 있으면 그 시점의 모든 PR이 같이 실패한다. 원인은 로그에 가려져 나오므로 같은 버전을 로컬에서 `gitleaks detect --redact -v`로 돌려 파일·줄·커밋을 찾는다.
- 오탐 처리: 테스트 코드에서 키처럼 보이는 문자열 리터럴(`const key = '...'`)을 없애고, 이미 올라간 커밋은 기록이 남으므로 `.gitleaksignore`에 지문(`커밋:파일:규칙:줄`)으로 등록한다. 히스토리를 다시 쓰는 강제 푸시는 쓰지 않는다.
- 로컬이 iCloud 동기화 폴더면 vitest 워커가 시간 초과로 뜨지 않는다. 테스트는 CI에서 확인한다. Mac에서 x86 JDK가 실행되지 않으면(`Bad CPU type`) arm64 JDK를 따로 받아 `JAVA_HOME`으로 지정한다.

### 8-8. 데이터를 읽을 때 주의

- **직접 방문(`(direct) / (none)`)은 출처를 알 수 없는 방문**이다. 주소 직접 입력, 북마크, QR, 카카오톡·문자로 받은 링크, 인스타 스토리·DM·일부 앱 내 브라우저가 여기에 섞인다. 인스타 프로필·게시글 링크는 `l.instagram.com / referral`로 따로 잡힌다. 직접 방문이 전부 인스타라고 단정할 수 없고, 구분하려면 링크에 UTM을 붙여 뿌려야 한다. UTM 링크는 **링크를 올리는 쪽(홍보 담당)이 만든다**. 사이트는 UTM이 붙어 들어오면 자동으로 읽고, 어드민 화면에도 캠페인 이름으로 나온다.
- 화면의 주문 수는 GA의 `order_submit` 이벤트 기준이라 **참고용**이다. 테스트 주문, 완료 화면 새로고침으로 인한 중복은 더 많게, 광고차단 환경은 더 적게 잡는다. 실제 주문 건수와 금액은 **주문 관리 화면**을 기준으로 한다.
- 요약의 "상품 조회 사용자", "주문 사용자"는 채널별 합이라 한 사람이 여러 채널로 들어오면 중복된다. 요약 전환율은 대략적인 값이다.
- 표준 보고서와 이 화면은 몇 시간 늦게 반영될 수 있다. 같은 기간은 15분간 같은 결과가 나온다.
- 로그인한 관리자 활동은 제외되지만, 제외 적용 이전 기간과 로그아웃 상태의 팀원 테스트는 섞여 있을 수 있다.

- [ ] 0절 기준으로 코드 직접 vs GTM 경유 결정
- [ ] GA4 속성 생성 (Asia/Seoul, KRW, 보관 14개월)
- [ ] 향상된 측정 "브라우저 기록 이벤트 기반 페이지 변경" 끄기
- [ ] 내부 트래픽 정의 생성 → 필터 테스트 확인 → 활성화
- [ ] (방식에 맞게) 2절 또는 3절대로 연결

- [ ] 키 이벤트 지정

- [ ] 팀원 뷰어 권한 추가
