# /commit - 커밋 메시지 제안 및 커밋

## 역할

변경사항을 확인하고 Conventional Commits 형식의 커밋 메시지를 제안한다.
사용자 승인 없이 커밋을 실행하면 안 된다.
커밋 후 push는 별도 사용자 승인 게이트를 거쳐야 한다.

## 실행 순서

### 1. 변경사항 확인

```bash
git status
git diff --cached
git diff
```

민감정보나 생성물이 포함되면 즉시 중단한다.

중단 대상 예:

- `.env`
- API 키, 토큰, 비밀번호
- `node_modules`
- `dist`

### 2. 관심사 분리 판단

변경사항이 여러 관심사에 걸쳐 있으면 단위별로 나눠서 커밋할 것을 제안한다.

예시:

```text
변경사항이 두 가지 관심사를 포함합니다.
1. 관리자 주문 필터 UI 수정
2. 주문 API 타입 보완

이 두 가지를 별도 커밋으로 나누시겠습니까?
```

### 3. 커밋 메시지 작성

형식:

```text
<type>: <한글 제목>

<본문 - 왜 변경했는지, 어떤 문제를 해결했는지>
```

type 종류:

| type | 사용 상황 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 기능 변경 없는 코드 개선 |
| `chore` | 빌드, 설정, 의존성 변경 |
| `docs` | 문서 변경 |
| `test` | 테스트 추가/수정 |
| `style` | 포맷, 공백 등 스타일 변경 |

제목 규칙:

- 한글로 작성
- 마침표 없음
- 변경 의도가 드러나게 작성

### 4. 사용자 승인 대기

제안한 커밋 메시지와 staging 대상 파일을 보여주고 승인 여부를 묻는다.

### 5. 커밋 실행

사용자가 승인한 경우에만 실행한다.

```bash
git add <파일 목록>
git commit -m "..."
```

`git add .` 또는 `git add -A`는 사용하지 않는다.

### 6. push 승인 여부 확인

커밋이 성공하면 현재 브랜치와 실행할 push 명령어를 보여주고 사용자 승인 여부를 묻는다.

```bash
git branch --show-current
git push origin <현재 브랜치명>
```

승인받은 경우에만 push한다.

## 주의사항

- main 브랜치에서 커밋 금지.
- push는 커밋 승인과 별개로 다시 승인받는다.
- force push 금지.
- 커밋 전 검증 명령 실행 여부와 결과를 함께 보고한다.
